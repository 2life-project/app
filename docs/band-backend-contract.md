# Контракт: данные браслета

Что мобильное приложение снимает с браслета и в каком виде готово отдавать на
сервер. Документ описывает **данные**, а не реализацию: формы полей взяты из
живого устройства и проверены на нём, эндпоинты — предложение, которое ждёт
подтверждения бэкенда.

Устройство: ES100, платформа `NAL-WB00`, протокол вендора UTE (диалект JX).
Связь — Bluetooth LE напрямую с телефона, без облака производителя.

---

## 1. Соглашения

Берутся те же, что уже действуют в `/api/v2`, чтобы браслет не заводил свой
диалект.

| Что             | Как                                                                 |
| --------------- | ------------------------------------------------------------------- |
| Транспорт       | HTTPS, JSON, `Content-Type: application/json`                       |
| Авторизация     | `Authorization: Bearer <accessToken>`, продление по 401 — как везде |
| Время           | ISO 8601 со смещением: `2026-09-09T14:32:00+03:00`                  |
| Идемпотентность | `requestId` в теле — как в существующих ручках записи               |
| Ошибки          | `{ "error": "<машинный код>", ... }`; клиент читает код, не текст   |
| Пагинация       | как в остальных списках; размер страницы обязателен в ответе        |

**Отдельно про время.** Браслет живёт по времени, которое ему выставил телефон
при подключении, и часового пояса не хранит. Все отметки приходят как локальное
время телефона. Клиент отдаёт их со смещением — сервер не должен считать, что
это UTC.

---

## 2. Идентификация устройства

```json
{
  "mac": "d8:0f:b5:11:2e:f7",
  "platform": "NAL-WB00",
  "firmware": "AT519V003396",
  "hardware": "010404",
  "protocol": "V1.0",
  "serial": "V1.0",
  "battery": { "level": 94, "charging": false, "lowBatteryAlert": false }
}
```

**Ключ устройства — `mac`, а не идентификатор из системы.** iOS не отдаёт
приложению адрес устройства: он выдаёт собственный UUID, свой на каждом
телефоне. Тот же браслет на втором телефоне получит другой UUID, и привязка по
нему развалит историю на две. MAC браслет отдаёт сам — и в рекламном пакете, и
в ответе на запрос информации.

Привязка сейчас **локальная**: живёт на телефоне и к аккаунту не привязана.
Если серверу нужна привязка к пользователю — это отдельная ручка, её в списке
ниже нет намеренно, потому что решение о модели владения устройством за вами.

## 3. Модель данных

### 3.1. Поминутный слот (`sample`)

Основной поток. Устройство копит слоты по минутам и отдаёт их кадрами за
период. За сутки — до 1440 слотов, реально меньше: пустые минуты устройство не
пишет.

```json
{
  "at": "2026-09-09T14:32:00+03:00",
  "steps": 118,
  "calories": 5,
  "distance": 85,
  "heartRate": 96,
  "averageHeartRate": 94,
  "restingHeartRate": 59,
  "minHeartRate": 88,
  "maxHeartRate": 104,
  "bloodOxygen": 97,
  "systolic": 124,
  "diastolic": 78,
  "hrv": 44,
  "mood": 3,
  "bloodSugar": null
}
```

| Поле                 | Единица    | Замечание                                                 |
| -------------------- | ---------- | --------------------------------------------------------- |
| `at`                 | —          | начало минуты, к которой относится слот                   |
| `steps`              | шаги       |                                                           |
| `calories`           | ккал       |                                                           |
| `distance`           | **метры**  |                                                           |
| `heartRate`          | уд/мин     | значение на момент слота                                  |
| `averageHeartRate`   | уд/мин     | среднее за слот                                           |
| `restingHeartRate`   | уд/мин     | приходит не в каждом слоте                                |
| `min/maxHeartRate`   | уд/мин     |                                                           |
| `bloodOxygen`        | %          |                                                           |
| `systolic/diastolic` | мм рт. ст. | приходят только парой                                     |
| `hrv`                | мс         |                                                           |
| `mood`               | 1–5        | шкала устройства, значения не документированы вендором    |
| `bloodSugar`         | ммоль/л    | поле в протоколе есть, датчика у ES100 нет — всегда пусто |

**Все поля кроме `at` — необязательные.** В одном слоте обычно два-три поля:
устройство пишет только то, что в эту минуту измеряло. Слот, где есть только
пульс, — норма, а не битые данные.

### 3.2. Сводка дня (`daySummary`)

Устройство считает дневные итоги само, по своим правилам. Они **не сходятся** с
суммой по слотам: базовый обмен идёт отдельным блоком. Итог берём у устройства.

```json
{
  "date": "2026-09-09",
  "steps": 8342,
  "distance": 6007,
  "calories": 512,
  "heartRate": 76,
  "measuredAt": "2026-09-09T14:31:00+03:00"
}
```

### 3.3. Сон (`sleepSegment`)

Стадии считает само устройство — клиент их не выводит и не пересчитывает.

```json
{
  "at": "2026-09-08T23:41:00+03:00",
  "minutes": 22,
  "stage": "light"
}
```

`stage`: `deep` | `light` | `awake` | `rem` | `nap` | `snore` | `sessionStart` |
`sessionEnd`.

`sessionStart` и `sessionEnd` — маркеры границ сессии, длительности не несут и
в подсчёт стадий не идут. `snore` устройство пишет, но микрофон под него не
задействует — считать это детектором храпа не стоит.

**Про нумерацию стадий.** В популярном публичном реверсе протокола третья и
четвёртая стадии перепутаны, из-за чего быстрый сон превращается в
пробуждения. Здесь взяты константы из SDK вендора: `3 = awake`, `4 = rem`.

### 3.4. Стресс (`stressSample`)

Отдельный канал, не слот. Устройство хранит посуточными блоками: время
полуночи, шаг и по байту на каждую минуту суток. Ноль означает «замера не
было», реальная сетка — примерно раз в десять минут.

```json
{ "at": "2026-09-09T14:20:00+03:00", "value": 59 }
```

`value`: 1–100, шкала устройства. Производная от вариабельности пульса, а не
отдельный датчик.

### 3.5. Разовый замер (`measurement`)

Результат ручного запуска: оптический датчик включается примерно на минуту.
Приходит отчётом, а не ответом на запрос.

```json
{
  "at": "2026-09-09T14:03:00+03:00",
  "heartRate": 82,
  "bloodOxygen": 97,
  "stress": 41,
  "hrv": 44,
  "systolic": 124,
  "diastolic": 78,
  "mood": 3
}
```

### 3.6. Ношение (`wear`)

```json
{ "at": "2026-09-09T14:32:00+03:00", "worn": true }
```

Нужно, чтобы отличать «пульса не было» от «браслет лежал в ящике».

### 3.7. Голосовая запись (`recording`)

```json
{
  "session": 1788248934,
  "startedAt": "2026-09-07T16:43:02+03:00",
  "bytes": 13280,
  "seconds": 6.64,
  "type": 1
}
```

`session` — время начала записи в секундах Unix. **Это и есть идентификатор
записи на устройстве**, другого у неё нет. Ключ идемпотентности — пара
`(deviceMac, session)`.

### 3.8. Память диктофона (`storage`)

```json
{ "total": 105519, "free": 105298, "bytesPerSecond": 2048 }
```

Единица — **килобайты** (выведена эмпирически: 86 440 байт заняли 84 единицы).
Итого около 103 МиБ, это примерно **15 часов звука**. Что происходит при
заполнении памяти — перезапись по кругу или отказ записи — не проверено.

## 4. Эндпоинты

Предложение. Формы тел — из раздела 3, здесь только обёртки.

### 4.1. Пачка показателей

```
POST /api/v2/band/samples
```

```json
{
  "requestId": "b1f2…",
  "deviceMac": "d8:0f:b5:11:2e:f7",
  "timeZone": "Europe/Moscow",
  "samples": [ { "at": "…", "heartRate": 96 }, … ]
}
```

Пачкой обязательно: история за период приезжает кадрами, по слоту на запрос —
это сотни вызовов на один день. Разумный потолок пачки — назовите свой,
клиент нарежет.

Идемпотентность: повтор той же пачки не должен плодить дубликаты. Естественный
ключ слота — `(deviceMac, at)`; при совпадении — перезапись, потому что
устройство может дослать в тот же слот поля, которых в первый раз не было.

**Ответ:** сколько принято и сколько отброшено как дубликаты.

### 4.2. Сводка дня

```
PUT /api/v2/band/day/{date}
```

Тело — раздел 3.2. `PUT`, а не `POST`: сводка за день одна, и в течение дня она
переписывается по мере поступления новых данных.

### 4.3. Сон

```
POST /api/v2/band/sleep
```

```json
{ "requestId": "…", "deviceMac": "…", "segments": [ … ] }
```

Ключ отрезка — `(deviceMac, at)`.

### 4.4. Стресс

```
POST /api/v2/band/stress
```

```json
{ "requestId": "…", "deviceMac": "…", "samples": [ … ] }
```

### 4.5. Разовые замеры

```
POST /api/v2/band/measurements
```

### 4.6. Голосовые записи

Три шага, потому что файл через обычный JSON-клиент не отправить.

**Шаг 1 — заявить запись и получить адрес для загрузки:**

```
POST /api/v2/band/recordings
```

```json
{
  "requestId": "…",
  "deviceMac": "d8:0f:b5:11:2e:f7",
  "session": 1788248934,
  "startedAt": "2026-09-07T16:43:02+03:00",
  "seconds": 6.64,
  "bytes": 13280,
  "format": "opus/ogg"
}
```

Ответ:

```json
{
  "id": "rec_01J…",
  "status": "awaiting_upload",
  "upload": {
    "url": "https://…",
    "method": "PUT",
    "headers": { "Content-Type": "audio/ogg" },
    "expiresAt": "2026-09-09T15:00:00+03:00"
  }
}
```

Если запись с такой парой `(deviceMac, session)` уже принята — вернуть её же с
`status: "uploaded"` и **без** `upload`. Это и есть защита от дублей после
обрыва.

**Шаг 2 — загрузка файла** по выданному адресу, мимо JSON-клиента.

**Шаг 3 — подтверждение:**

```
POST /api/v2/band/recordings/{id}/uploaded
```

Дальше расшифровка на вашей стороне. Клиенту нужно уметь спросить результат:

```
GET /api/v2/band/recordings/{id}
```

```json
{
  "id": "rec_01J…",
  "status": "transcribed",
  "seconds": 6.64,
  "transcript": { "text": "…", "language": "ru", "segments": [ … ] }
}
```

`status`: `awaiting_upload` | `uploaded` | `transcribing` | `transcribed` |
`failed`.

**Почему нужен адрес для загрузки, а не multipart на ваш сервер.** Час звука —
около 7 МБ, а память браслета вмещает пятнадцать часов. Загрузка идёт с
телефона в фоне, ей нужен докачиваемый адрес и своя таймаутная политика.
Multipart через основной API это всё ломает. Если presigned-адресов у вас нет —
скажите, клиент будет слать multipart на отдельный хост.

## 5. Аудио: формат

Разобран на живом устройстве, проверен декодированием.

| Свойство        | Значение                                          |
| --------------- | ------------------------------------------------- |
| Кодек           | **Opus**, сырой поток без контейнера              |
| Частота         | 16 000 Гц                                         |
| Каналы          | 1 (моно)                                          |
| Битрейт         | **16 кбит/с, жёсткий CBR**                        |
| Кадр            | 20 мс                                             |
| Пакет           | 40 байт                                           |
| Скорость потока | ровно **2000 байт в секунду**                     |
| Длительность    | `bytes / 2000` секунд — точно, без разбора потока |

Устройство отдаёт **сырой поток Opus**, без контейнера. Клиент упаковывает его
в **Ogg** (заголовки `OpusHead` / `OpusTags`, CRC32 по спецификации Ogg) и
сохраняет как `.ogg` — файл открывается любым плеером и принимается любым
распознавателем.

Первые байты потока — `4B 41` — это **не сигнатура формата**, а TOC-байт Opus
плюс счётчик кадров. Искать по ним магическое число бессмысленно.

Имя файла на телефоне: `<session>.ogg`, после выгрузки — `<session>.sent.ogg`.

**Оценки объёма:**

- 1 минута ≈ 120 КБ
- 1 час ≈ 7,2 МБ
- полная память браслета ≈ 103 МиБ ≈ 15 часов

## 6. Порядок синхронизации

Как это работает на телефоне сейчас, чтобы вы понимали характер нагрузки.

1. Приложение подключается к запомненному браслету само, при открытии раздела.
2. Читает по очереди: информацию, сводку дня, список записей, память, сон,
   стресс, поминутную историю. История последняя — она идёт кадрами и дольше
   всего остального вместе взятого.
3. Пока раздел открыт, устройство само шлёт живые отчёты примерно раз в десять
   секунд; сводка дня опрашивается раз в тридцать секунд.
4. Записи выгружаются на телефон отдельным проходом, по одной за раз, в том
   числе фоновой задачей.

**Что это значит для вас.** Данные приезжают не потоком, а пачками при
подключении, и одна пачка может нести целые сутки. iOS не даёт держать фоновую
синхронизацию постоянно — реально она случается при открытии приложения и в
редкие фоновые окна, которые система выдаёт сама. Поэтому пачки нужны, а
поштучная отправка не годится.

## 7. Коды ошибок, которые нужны клиенту

| Код                        | Когда                                              |
| -------------------------- | -------------------------------------------------- |
| `band_device_unknown`      | устройство не привязано к пользователю             |
| `band_sample_out_of_range` | отметка времени вне допустимого окна               |
| `band_batch_too_large`     | пачка больше лимита — назовите лимит в теле ответа |
| `band_recording_exists`    | запись с такой `session` уже принята               |
| `band_upload_expired`      | адрес загрузки протух, нужен новый                 |

Текст ошибки в интерфейс не идёт — экран выбирает формулировку по коду.

---

## 8. Что уже готово на клиенте

Всё, что описано в разделе 3, приложение **уже читает с устройства** и держит
локально: поминутная история, сводка дня, сон по стадиям, стресс, разовые
замеры, состояние ношения, список записей, память, голосовые файлы в Ogg.

Отправлять некуда — ручек нет ни одной. Как только они появятся, клиенту
останется подключить отправку: слой данных, разбор протокола и локальное
хранилище уже на месте.

## 9. Открытые вопросы

1. **Модель владения устройством.** Браслет привязан к телефону или к аккаунту?
   Сейчас привязка локальная. Если нужен второй телефон на тот же аккаунт —
   ключом должен быть MAC, и это ваше решение, а не наше.
2. **Глубина хранения на устройстве** не проверена: сколько дней истории
   переживает браслет до перезаписи — неизвестно.
3. **Поведение при полной памяти диктофона** — перезапись по кругу или отказ
   записи — не проверено.
4. **Распознавание речи**: чьё, с какой задержкой, нужен ли клиенту прогресс.
5. **Лимит пачки** и **окно допустимых отметок времени** — назовите свои.
6. **Нужны ли вам сырые данные или производные.** Клиент умеет считать темп,
   длину шага, скорость, эффективность сна, циклы, зоны пульса и стресса. Если
   это нужно на сервере — считайте у себя из слотов, дублировать вычисления в
   двух местах не стоит.
