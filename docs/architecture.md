# Архитектура

Цель одна: чтобы через год было понятно, куда класть новый код, и чтобы удаление
фичи не разбирало половину приложения. Отсюда четыре слоя и жёсткое направление
зависимостей.

Схема — урезанный Feature-Sliced Design: из семи его слоёв взяты три
(`app`, `features`, `shared`) плюс отдельный `core` для инфраструктуры.
Сама методология рекомендует начинать именно так и заводить `entities` и
`widgets` только когда они начнут окупаться.

## Слои

```
src/app        экраны и маршруты expo-router
     ↓
src/features   продуктовые области
     ↓
src/shared     переиспользуемое без знания о продукте
     ↓
src/core       инфраструктура
```

Стрелка вниз — «может импортировать». Наверх — никогда.

### `src/core`

Всё, что не зависит ни от продукта, ни от React: чтение окружения, HTTP-транспорт,
логи. Здесь нет слова «анализ», «показатель» или «врач».

- `config/env.ts` — единственное место чтения `process.env`. Значения `EXPO_PUBLIC_*`
  инлайнятся в бандл, поэтому секретов там нет и быть не может.
- `http/client.ts` — базовый адрес, JSON, таймаут, разбор ошибки в `HttpError`.
  Продуктовые эндпоинты сюда не добавляют.
- `log/logger.ts` — вместо `console`, который запрещён линтером.

### `src/shared`

То, чем пользуются несколько фич. Знает про дизайн, не знает про продукт.

- `theme/` — токены в три уровня: сырые шкалы, смысловые роли, тема.
  Единственный источник цвета, кегля, отступа, радиуса, тени и длительности.
  Правила — в [design-tokens.md](design-tokens.md).
- `ui/` — базовые компоненты: `Screen`, `Text`, `Stack`, `Card`, `Button`, `Tag`,
  `EmptyState`. Компонент попадает сюда, когда его просит **вторая** фича,
  не раньше.

### `src/features/<имя>`

Одна продуктовая область целиком: экраны, состояние, запросы.

```
features/home/
├── index.ts     публичный вход — только он виден снаружи
├── model/       логика без React: чистые функции, типы, состояние
└── ui/          экраны и блоки
```

- `api/` появляется, когда у фичи есть свои запросы; он зовёт `@/core/http/client`.
- Наружу торчит только то, что перечислено в `index.ts`.
  `import { X } from '@/features/home/ui/home-screen'` запрещён линтером.
- Фичи не импортируют друг друга. Понадобилось общее — оно едет в `shared`.

### `src/app`

Только маршруты expo-router. Файл экрана подключает фичу и заканчивается:

```tsx
import { HomeScreen } from '@/features/home';

export default HomeScreen;
```

Логика, запросы и вёрстка на уровне маршрута — ошибка слоя.

## Как это удерживается

Не договорённостями, а линтером — `eslint.config.js`:

| Правило                      | Что ловит                        |
| ---------------------------- | -------------------------------- |
| `import/no-restricted-paths` | импорт наверх по слоям           |
| `no-restricted-imports`      | обход публичного `index.ts` фичи |
| `no-restricted-syntax`       | hex-литерал вместо токена        |
| `no-console`                 | логи мимо `logger`               |
| `import/order`               | порядок и группировку импортов   |

`make check` = формат + линтер + типы + тесты. Ровно это гоняет CI на каждый PR.

## Как добавить

**Экран в существующий раздел.** Файл в `src/app/(tabs)/` → компонент из фичи.
Появилась логика — она уезжает в `features/<имя>/model`, не остаётся на маршруте.

**Новый раздел таббара.** Файл в `src/app/(tabs)/` плюс `Tabs.Screen` в
`src/app/(tabs)/_layout.tsx`. Больше нигде.

**Новая фича.** Каталог `src/features/<имя>/` с `index.ts`, `ui/`, `model/`.
Экспортировать наружу минимум: обычно один экран.

**Новый общий компонент.** В `src/shared/ui/` плюс строка в `src/shared/ui/index.ts`.
Стили — обычный `StyleSheet.create` с импортом `theme`.
Логики продукта в нём быть не должно.

**Новый запрос.** `features/<имя>/api/` поверх `request` из `@/core/http/client`.

## Решения и почему

- **Expo, а не голый React Native CLI.** Обновления SDK одной командой, OTA,
  сборка без локального Xcode. Нативные модули доступны через dev build.
- **expo-router, а не react-navigation вручную.** Маршрут = файл, типизированные
  ссылки, deep links из коробки.
- **Токены как обычный TypeScript, без библиотеки стилей.** `StyleSheet` и
  импорт темы решают задачу без нативного модуля и babel-плагина, которых
  требуют Unistyles и NativeWind. Понадобятся варианты и брейкпойнты —
  меняется слой стилей, форма токенов остаётся.
- **Шкалы считаются, а не подбираются.** `make tokens` строит их в OKLCH и
  подгоняет заливки под контраст AA; тесты пересчитывают контраст независимо.
  Генератор и есть дизайн-система: фирменный цвет входит в него полем рецепта,
  а не правкой сгенерированного файла.
- **Тема одна.** Тёмной не будет, пока нет её макета: провайдер и хук ради
  одной темы — сложность в каждом компоненте без единого потребителя.
  Возврат стоит второй карты ролей и перевода компонентов на хук.
- **`ios/` и `android/` не в репозитории.** Единственный источник нативной
  конфигурации — `app.json`; правки в Xcode переживают ровно до `make prebuild`.
